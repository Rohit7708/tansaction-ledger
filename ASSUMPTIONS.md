# Assumptions and Design Decisions

## Accounts

- A new account always starts with a balance of **0.00**. The balance cannot be supplied by the client; the only way
  to change it is through transactions or transfers.
- Account names are trimmed, must contain at least one non-whitespace character and are at most 100 characters.
  Control characters (including NUL and newlines) and invalid Unicode are rejected.
  Names are not unique (two customers can share a name).
- Accounts cannot be renamed or deleted through the API (not required; deleting an account would orphan its ledger).
- `GET /api/accounts` returns every account, newest first, without pagination. That is fine for the expected data
  volume of this assessment; a production system would paginate it like transaction history.

## Money

- Single currency; no currency code is stored or displayed.
- Amounts are stored as PostgreSQL `NUMERIC(19, 2)` and handled in the backend with `Prisma.Decimal`
  (decimal.js). JavaScript floating-point numbers are never used for monetary arithmetic. In the frontend, the
  combined balance is summed in integer cents with `BigInt`.
- Amounts in responses are always strings with exactly two decimals, e.g. `"100.00"`.
- Amounts in requests may be a string (recommended) or a JSON number. They must be plain decimals with at most two
  fraction digits, strictly greater than zero, and at most `1,000,000,000.00` per transaction or transfer. Exponent
  notation, signs, leading zeros, `NaN` and `Infinity` are rejected. Values with more than two decimals are
  **rejected, not rounded**.
- The direction of a transaction comes from `type`. Amounts are always positive, so a negative amount can never be
  used to reverse the meaning of a credit or debit.

## Transactions

- `type` is `"credit"` or `"debit"` (lowercase in the API; stored as a PostgreSQL enum `CREDIT`/`DEBIT`).
- `reference_id` is a client-supplied idempotency key: required, trimmed, 1–100 characters from
  `A-Z a-z 0-9 . _ : / -`.
- **Reference IDs are unique per account**, enforced by `UNIQUE (account_id, reference_id)`. The same reference may
  be used on different accounts.
- A duplicate reference is rejected with `409 DUPLICATE_TRANSACTION` even if the type, amount or description differ.
  The server does not "replay" the original response; the client can read the history to find the original entry.
- If a request with a reference is **rejected** (insufficient balance, validation error, database failure), nothing is
  stored, so the reference is not consumed and the client may retry with it later.
- When a retry of a successful debit arrives after the balance has dropped, the response is
  `DUPLICATE_TRANSACTION` rather than `INSUFFICIENT_BALANCE`, because the duplicate check happens first. Clients can
  therefore tell "already done" apart from "cannot be done".
- References starting with `transfer:` are reserved for the ledger entries created by transfers.
- `description` is optional, trimmed, at most 255 characters, and defaults to an empty string. Control characters
  (including NUL and newlines) and unpaired UTF-16 surrogates are rejected with 400: PostgreSQL cannot store NUL
  and invalid Unicode cannot be encoded, so accepting them would otherwise fail with a 500.
- `created_at` (and every `id`) is generated by the database. Client-supplied timestamps, ids or balances are
  rejected as unknown fields.

## Immutability

- Transactions and transfers are append-only. The API has no update or delete endpoints for them, unsupported HTTP
  methods return `405`, and a PostgreSQL trigger rejects `UPDATE`/`DELETE` on those tables as defense in depth.
- Mistakes are corrected with a **compensating transaction**, for example a credit that reverses an erroneous debit.
  This keeps a complete audit trail.
- `TRUNCATE` is not blocked, so the test suite can reset its dedicated database.

## Balance consistency

- The stored balance is a denormalized cache of `Σ credits − Σ debits`. It is changed only in the same database
  transaction that inserts the corresponding ledger row, after locking the account row.
- `CHECK (balance >= 0)` guarantees that no code path can persist a negative balance.
- Failed, duplicate and rejected requests roll back completely and never change a balance. The test suite checks this
  by recomputing balances from the ledger with SQL and comparing them with the stored value.

## Pagination and ordering

- `page` defaults to 1 and `limit` to 10. Both must be positive integers. `limit` above **100** is rejected with
  `400 INVALID_PAGINATION` (not silently clamped), so clients notice the mistake.
- Requesting a page past the end returns `200` with an empty `data` array and accurate metadata.
- Results are ordered by `created_at DESC, id DESC`. `id` is a tie-breaker that makes the order deterministic when
  timestamps are equal. A composite index on `(account_id, created_at DESC, id DESC)` supports this query.
- The count and the page of rows are read in one `REPEATABLE READ` snapshot, so `total_records`/`total_pages`
  always agree with `data`, even while new transactions are being committed.
- Offset pagination is used, as specified. Under concurrent inserts, a page boundary can shift between requests.
  Cursor (keyset) pagination would avoid that and is a natural next step.

## Transfers

- Source and destination must exist and differ. The amount follows the same rules as a transaction.
- A transfer creates one `transfers` row plus one DEBIT entry on the source and one CREDIT entry on the destination,
  all in a single database transaction. Both ledger entries are linked by `transfer_id` and share the reference
  `transfer:<reference_id>`.
- **Idempotency:** the transfer `reference_id` is **globally unique** (`UNIQUE` on `transfers.reference_id`). A
  retry with the same reference returns `409 DUPLICATE_TRANSFER` and moves no money. This holds even when the
  original request is still in flight, because the competing transactions serialize on the account row locks and the
  unique constraint.
- Accounts are locked in ascending id order, so opposing transfers (A→B and B→A) cannot deadlock.
- Transfer reference IDs live in a separate namespace from transaction references (`transfer:` prefix), so they
  never collide with a reference the client used for an ordinary credit or debit.

## Error responses

- Every error has the shape `{ "success": false, "error": { "code", "message", "details?" } }`.
- Status codes: 400 for invalid input, 404 for missing resources or routes, 405 for unsupported methods,
  409 for business conflicts (duplicates, insufficient balance), 413 for bodies over 10 KB, 500 for anything
  unexpected. The full mapping is in [docs/api.md](docs/api.md).
- Unexpected errors are logged server-side (method, path, error and stack) without request bodies. The client
  receives only a generic message.

## Out of scope

- Authentication and authorization (not required by the assessment). In production, every endpoint would require an
  authenticated principal and account ownership checks.
- Multi-currency, interest, fees, account closure and rate limiting.
